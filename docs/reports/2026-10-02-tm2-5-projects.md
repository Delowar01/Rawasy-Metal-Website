## 9. Anchor fix architecture

The problem (reported in TM-2.4): `commerce.css` set `scroll-behavior: smooth` on `html` from the first paint, so the
browser's jump to an address's `#anchor` glided. Chromium keeps an instant fragment jump on its target through layout
changes until the load event. A gliding jump keeps the position it set out for, so a web font arriving on the way left
the target short or under the sticky header.

The fix changes only the timing and mode of the first jump, not its target or any design:

- `commerce.css`: `scroll-behavior: smooth` now applies only to `html[data-smooth-scroll]`. The landing still comes from
  the existing `scroll-padding-top` (header + 1 rem). On the projects page it also uses one CSS token for the bar
  (item 18).
- `commerceBoot` (the inline boot script) sets `data-smooth-scroll` after the load event, then `document.fonts.ready`,
  then two animation frames, so the browser's last correction is laid out first. `BootFallback` (the browser-built 404)
  runs it on a page that has already loaded.
- Reduced motion: the existing unlayered `@media (prefers-reduced-motion: reduce) { html { scroll-behavior: auto } }`
  outranks the layered attribute rule, so every jump stays instant.
- Without script the attribute never comes, so every jump is instant (item 29).
- No scroll engine, no timer, no page-specific offset: it reacts to events (load, fonts, frames), and the browser does
  every scroll itself.

Measured on cold loads (a new context each time, fonts held back 0 / 300 / 1500 ms), at 1440 and 390, on `/en/contact#quote`,
`/en/contact#location`, `/en/privacy#contact`, `/ar/terms#contact`, `/en/services/laser-cutting#gallery` and
`/ar/services/fabrication#projects`:

| | before | after |
|---|---|---|
| off at the load event | 26 of 36 (24 still gliding, 192–11,043 px from their place; 2 landed 95–107 px off) | 0 of 36 |
| off after idle | 12 of 36 (64–309 px, under the header every time) | 0 of 36 |
| off 5 s later (legal pages) | — | 0 |
| every 50 ms over the first 700 ms (three addresses, both widths) | — | 0 off at every sample |

The same-page glide is unchanged: a click on Contact's address row still glides (more than 5 distinct frames), and Back
and Forward return to each place.

## 16. Filter state

- `ProjectFilterProvider` holds one choice (`"all"` or a category) for the hero's `QuickFilter`, the bar and the wall.
- Nothing is stored, so every visit starts on "All".
- Items the choice leaves out get the `hidden` attribute: out of the layout and the accessibility tree.
- A choice from the bar re-flows the wall with the browser's animated page update (`document.startViewTransition` +
  `flushSync`, item 30). From the hero, or while the bar is pinned over the wall, it applies at once; the pinned case
  then restarts the wall just under the bar with an instant `scrollIntoView`.
- A link to a hidden project clears the choice first:
  - a document click listener in the capture phase sees the link before the browser follows it and sets "All" with
    `flushSync`, so the browser's own jump lands on a shown item (no script scrolling at all);
  - an address or history entry naming a hidden project clears it on `hashchange`, then `scrollIntoView`.
  - Nothing ever scrolls to an item while it is `hidden`, and there is no `scrollTo` arithmetic.
- The test records, at the moment the browser starts its jump, whether the target is still hidden (a click listener on
  `window` runs after the page's and before the default action): never, for an index link, a highlight and the
  featured project's action.

## 18. Sticky bar architecture

- `.pj-bar` is `position: sticky` at `top: var(--hh)` (the header's height), with its height from one token,
  `--pj-bar-h: 3.5rem` (56 px), on `.pj-gallery`.
